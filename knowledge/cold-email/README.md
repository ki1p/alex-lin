# 买家视角开发信：他 → 痛 → 证 → 轻

核心：买家买的是他自己的理由。首封信应让具体收件人看出你做过研究，并给出容易回复的理由。

2026-11-05补充融合：[从可交付价值到可兑现标题](value-to-subject.md)。将Jingsourcing模式笔记与标题三法则串成“确认合作阶段→选择可交付价值→写客户相关标题→正文兑现→试单与后续经营”的流程。

## 在工作台使用

1. 在“客户与开发信”选择客户，打开“开发信助手”。填写已确认姓名、职位、客户事实及来源与日期、目标、单项产品、对应价值、可验证案例和具体下一步。
2. 点击“整理 GPT 提示词”，检查资料后复制给 GPT。此按钮只在本机整理文字，不请求在线模型。生成时要求三个客户相关主题（各≤8个英文词）、英文正文、中文回译、简短自评和资料缺口。
3. 选择一个主题，把审阅后的英文正文与中文回译填回原编辑器。中文仅供内部查看。“保存草稿”会一起保存写作资料；关闭前请保存。
4. 点击“检查当前开发信”。预览时也会显示提示。机器检查词数、泛称、部分规模介绍、感叹号、占位符及已记录来源的缺口；无法验证网页真实性、数字真实性、语义相关性或是否会获得回复。
5. 人工核验后沿用原有预览、加入队列与启动发送操作。助手不自动排期或发送，也不会重写旧草稿。公司全部邮箱分别准备时共用该公司事实，但个人姓名与实际收件人必须逐一核实。
6. 新增可选资料：获客来源／合作阶段、可验证服务能力及边界、小批试单条件、标题承诺依据。这些资料同样随草稿保存；旧草稿不要求补填。无数字与交期依据时可留空，提示词会要求使用具体但不量化的标题。

## 写作规则

| 环节 | 要求 |
|---|---|
| 他 | 用已确认的名字；主题说客户的事；前两句引用有来源的具体事实。 |
| 痛 | 只围绕一个客户目标。官网业务范围不等于正在采购；未确认问题用条件式提问。 |
| 证 | 能力必须对应目标并说明适用范围；结果须可验证且允许披露。没有案例就省略，并列出缺口。 |
| 轻 | 只给一个具体、低门槛、30秒内能回复的下一步，例如是否发送一页方案。 |

- 不使用 Dear Sir / Dear Boss / Dear Customer、“尊敬的客户”等泛称；未知姓名先补资料，不编造。带 `[FirstName]` 的稿件只作待补草稿。
- 删除厂房面积、工人数、产线数、经验年数、领先、更专业、更便宜等与当前目标无关的自我介绍。允许必要的身份署名与可验证的产品适用信息。
- 正文建议80–120个英文词，含称呼、不含主题与署名。不写模板寒暄、形容词堆砌、感叹号或“期待合作”式空话。
- 主题备选三条，每条≤8词并注明适用场景。自评解释回复理由，不承诺回复率。
- 标题有数字、交期、性能、免费样品或认证等承诺时，记录依据与适用条件，并逐项核对正文。数字／时间不是硬性要求；不以吸引打开为理由编造承诺。机器只能提示数字是否出现，无法验证语义、单位与条件一致性。
- 默认按陌生首封，已确认询盘、试单或复购背景时才调整表达。只使用本方可交付服务，不照搬其他公司的整条链路；不因小单直接否定价值，也不擅自承诺免费或无条件接单。
- 自动词数按英文单词／数字计算；带连字符和撇号视作一个词，常见英文署名前截断。非英文邮件不适用此词数建议。

## 发信前60秒

- 主题和前两句是否具体到这家公司？事实有来源、日期且与实际收件人对应吗？
- 是否只讲一个客户目标，而非堆我方产品？不确定的痛点是否写成提问？
- 姓名、技术信息、案例数字和披露权限是否核实？所有占位符是否清除？
- 标题每项承诺是否在正文及报价／技术资料兑现？来源与有效期、单位、费用、交期起算是否一致？合作阶段和试单条件是否有依据？
- 下一步是否具体且容易回复？
- 换一家公司仍完全适用吗？如果是，继续定制。
